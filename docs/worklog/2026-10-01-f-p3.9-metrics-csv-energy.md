# 2026-10-01 — P3.9's first real metrics.csv: electricity/gas

- **Phase / tasks:** P3.9
- **Branch / PR:** `phase-3-metric-table` / not opened
- **Agent / person:** agent (routine firing)

## Goal

Build on the previous firing's `export.py` core (ADR-0010) and actually
produce a real `data/processed/metrics.csv` for at least one metric pair,
end to end: live fetch -> apportion -> compute -> export.

## Done

- Scoped this firing to metrics 3/4 (electricity/gas) rather than
  attempting all four core metrics at once: their apportionment data
  (`data/processed/geography/weights.csv`, P1.5/P3.4) and fetchers
  (`fetch.desnz_lsoa_energy`) are already structured and committed, so
  the integration doesn't need any further ad hoc live research (unlike
  canopy's per-comparator Forest Research ward-name matching, or
  greenspace's England-wide clip, whose real IDs/mappings only exist in
  this session's prose/test fixtures, not as reusable config/data).
- `fetch/http.py` gained a public `latest_manifest(source_id)` (wrapping
  the existing private `_latest_manifest`) -- exactly the helper the
  P3.9 handoff notes anticipated an orchestration script would need, to
  read a specific fetch's own `retrieved_at`/`sha256` right after it
  returns (per ADR-0010, not re-discovered later). 2 new tests.
- Built `pipeline/scripts/build_metrics_csv.py`:
  - Loads `geography.yaml`, `sources.yaml`, and `weights.csv` (real,
    committed, never hand-edited).
  - For each fuel: fetches live LSOA-level DESNZ data for the union of
    every subject/comparator parish's contributing LSOAs, and live
    regional/LA data for South Oxfordshire + England.
  - Routes each area through the right existing `compute_*_row` function
    (`compute_subject_energy_row` for Cholsey/Moulsford's real NSUL
    address-count weights, `compute_comparator_energy_row` for the other
    7 parishes' area weights, `compute_area_energy_row` for
    district/national) -- no new metric logic, just wiring.
  - Calls `export.build_metrics_row` for every row, with each fetch's
    real `latest_manifest(...)` provenance, then `rows_to_dataframe` /
    `write_metrics_csv` / `write_readme`.
- Ran it live. Real result: **22 rows** written to
  `data/processed/metrics.csv` (9 areas x 2 fuels + district x 2 +
  national x 2), all passing `METRICS_CSV_SCHEMA` validation, plus a
  real `data/processed/README.md` summary. The repeat live fetch mostly
  hit DESNZ's conditional-request cache (same `ETag`/`Last-Modified` as
  P3.4's original fetch), so the manifest's `retrieved_at` correctly
  stayed at the original download time, only `row_count`/
  `query_signature` updated to reflect the wider LSOA code set this
  script queries (all 9 areas at once, not just Cholsey/Moulsford's 3).
- **Cross-checked every value against what was already documented**: the
  script reproduced Cholsey's 3,682.27 kWh/meter electricity and
  11,000.81 gas, England's 3,352.84 electricity, South Oxfordshire's
  12,439.93 gas -- exactly matching P3.4's original live-verified
  figures, confirming the integration script is a faithful re-assembly
  of the real pipeline, not a new, divergent calculation.

## Decisions

- No new ADR -- straightforward application of ADR-0010's already-decided
  pattern, and reuse of already-accepted `metrics/energy.py` logic.
- Scoping judgement: electricity/gas only this firing, not all 4 core
  metrics. Canopy/greenspace need real per-area reference data
  (comparator ward codes; area boundaries) that currently exists only as
  prose/test-fixture knowledge from earlier live research, not a
  reusable file the way `weights.csv` is for energy -- attempting them
  without that foundation risked re-deriving (or misremembering) real
  IDs rather than genuinely re-verifying them live, which the project's
  "never guess a value" rule exists to prevent. Logged as the next step
  rather than rushed.
