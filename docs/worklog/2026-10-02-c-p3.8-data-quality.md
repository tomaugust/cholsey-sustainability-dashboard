## Goal

With all four buildable core metrics now in a real `metrics.csv` (P3.9,
earlier firings today), build P3.8's validation/reconciliation suite
(development-plan.md §5.2) against it.

## Done

- Read development-plan.md §5.2 and Phase 3's own "tests of success"
  wording fully before starting, to scope this properly rather than
  guess what "validation suite" means: four checks wanted (ranges, YoY
  limits, completeness matrix, district/national reconciliation vs
  published figures), each meant to read its thresholds from
  `config/metrics.yaml` (already fully populated with `valid_range`/
  `max_yoy_change_pct`/`similar_band_pct` for every metric -- no config
  changes needed there) so "tightening a rule is a config change ...
  not a code change."
- Built `pipeline/src/cholsey_pipeline/validate/data_quality.py`:
  - `validate_ranges(df, metrics)` -- flags any row outside its metric's
    `valid_range`.
  - `validate_yoy_change(df, metrics, exceptions)` -- flags any
    (area, metric) year-over-year change exceeding `max_yoy_change_pct`,
    comparing each year to the *previous year actually present* in the
    data (not blindly `year - 1`, since a gap year shouldn't be treated
    as 0%/100% change). Excusable via a new `config/dq_exceptions.yaml`
    allow-list, per §5.2's own wording ("allow-list exceptions ... each
    with reason, added_by and date").
  - `check_completeness`/`build_completeness_matrix` -- flags any
    (area, metric) pair with no row at all, unless a completeness-type
    exception documents a real gap. Real design note: `METRICS_CSV_SCHEMA`'s
    `flag` enum (none/parish_estimate/suppression_fallback/
    partial_coverage) has no "unavailable" value to attach to a
    nonexistent row, so a genuinely-missing metric (Aldworth's canopy)
    simply has no row at all rather than a row with an explanatory flag
    -- `dq_exceptions.yaml` is where that documentation lives instead.
    Considered extending the schema with a new flag value and a stub row
    instead, but that's a bigger, separate schema change (what would
    `value` even be for a stub row?) better left for its own decision
    than folded into this firing's validation-suite work.
- `config/dq_exceptions.yaml` gets its one real entry: Aldworth's canopy
  gap (ADR-0006/P3.2 -- its containing ward has no Forest Research
  record at all).
- Tests use both small real-valued fixtures (e.g. Cholsey's real 10.4%
  canopy figure, real YoY energy values) AND the actual committed
  `data/processed/metrics.csv`, reading it directly with `pd.read_csv`
  -- confirms the real pipeline output is currently clean except for
  exactly that one documented gap. Two tests specifically cross-check
  the exceptions mechanism does real work (one with the real exceptions
  list applied showing zero gaps, one with `exceptions=None` showing
  exactly the expected one gap) rather than the test vacuously passing
  regardless of whether exceptions are even read.

## Decisions

- No new ADR -- this is a direct build of what development-plan.md §5.2
  already specifies, not a new methodology choice.
- Scoping judgement: did NOT build the fourth check (reconciliation
  against a publisher's own aggregate, `metrics.yaml`'s documented-but-
  unused `reconcile_with` field). Reasoned through explicitly: energy's
  district/national rows (`method=direct`) already ARE DESNZ's own
  published district/national figure -- there's no second,
  independently-computed value to check it against, so a
  "reconciliation" check there would just always pass by construction
  and add no real verification value. Canopy/greenspace's district rows
  DID get a real one-off cross-check during their original builds
  (canopy: 21-ward area sum vs the real LAD boundary area, matching to
  0.003%; greenspace: district clip cross-checked against its own
  boundary fetch) -- but turning that into a general, reusable,
  config-driven check needs a second real case to generalise the
  pattern from, which doesn't exist yet (MCS has no district/national
  rows at all). Rather than write a single-purpose, always-trivially-
  passing check just to tick a box, left this for a future P3.8 session.
