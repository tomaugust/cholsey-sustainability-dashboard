## Goal
Write the real `config/sources.yaml`, `config/geography.yaml` and `config/metrics.yaml` from the spec, and add integration tests that load them through P0.3's registry loaders (rather than only fixture-based unit tests).

## Done
- `config/metrics.yaml`: all 7 metrics from spec §3 (6 core + EPC as `stretch: true`), each with `label`/`unit`/`direction` (required by the loader) plus `valid_range`, `max_yoy_change_pct`, `similar_band_pct` and `spec_ref` for later phases (development-plan.md §5.2). Added a `tile_groups.home_energy` entry combining `electricity` + `gas`, implementing the Q-002 resolution (five home-page tiles from six core metric_ids).
- `config/geography.yaml`: Cholsey (subject, `E04012474`, with the spec's area/population/postcode facts), South Oxfordshire (district, `E07000179`), England (national, `E92000001` — the standard ONS code, per the Q-003 default), plus the two overlapping LSOAs, the MSOA and the ward from spec §2.
- **Important honesty call:** the spec names five candidate comparator parishes by name only, with no GSS codes, and explicitly says to confirm them against the ONS boundary layer (Phase 1, P1.1-P1.3). Rather than invent plausible-looking `E04xxxxxx` codes I have not actually looked up — which would quietly defeat the whole project's traceability requirement the moment anyone trusted them — I keyed each candidate by a `PENDING-<slug>` placeholder id with `pending_confirmation: true` and no fabricated code, and wrote a prominent comment at the top of the file explaining why. Added a test that actively enforces this (`test_comparator_parishes_are_explicitly_flagged_pending`) so a future run can't accidentally "fix" this by filling in guessed codes without going through Phase 1's real boundary lookup.
- Kept county (Oxfordshire) and region (South East) out of the `areas:` block entirely — they don't fit the loader's `subject/comparator/district/national` role enum and aren't spec benchmark levels — and put them under a separate `reference_geographies:` key instead, so `load_geography` doesn't have to accept a misleading role for them.
- `config/sources.yaml`: all 7 metric-data sources from spec §4 (Forest Research canopy, OS Open Greenspace, DESNZ LSOA energy, DESNZ postcode energy, MCS installations, ONS population/dwellings, DLUHC EPC), each with `name`/`publisher`/`licence`/`attribution_text` (required) plus `url`/`resolution`/`cadence`/`format`/`notes`/`fetcher` pointers to the Phase 2 work package that will implement it. Also registered the two ONS boundary datasets (spec §2) since Phase 1 needs the same traceability for the geographic join itself, not just metric values. MCS's `licence` field is left as `"TBD — confirm licence/terms before bulk use"` rather than guessed, since P2.7 is specifically tasked with investigating MCS data access (plan risk R1).
- `pipeline/tests/unit/test_registry_real_config.py`: 12 new tests loading the real files via the default `CONFIG_DIR` (not fixtures) — covers metric count/ids, the home_energy tile group, England as the national default, the PENDING-* comparator enforcement above, and that every source has a URL.

## Decisions
- No new ADR. This is content, not architecture — followed ADR-0002/development-plan.md §2.3 as written.
- The "don't fabricate GSS codes" call above is a judgement call worth flagging even though it's not ADR-worthy: it means Phase 1's P1.3 (comparator confirmation) is now a slightly more visible blocker for Phase 3 than it might otherwise have looked, since the placeholders make it obvious in the data itself, not just in a spec footnote. That's intentional.
- county/region → `reference_geographies:` rather than forcing a role: this keeps `load_geography`'s enum honest; noted in the file's own comments for the next agent.
