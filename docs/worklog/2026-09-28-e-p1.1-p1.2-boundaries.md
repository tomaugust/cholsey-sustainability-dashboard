## Done
- **Looked up the real ONS Geoportal dataset identities and FeatureServer URLs** via the portal's public search API (`https://geoportal.statistics.gov.uk/api/search/v1/collections/dataset/items?q=...`) rather than guessing them from memory. A first guessed URL (constructed from a plausible-looking dataset name) returned HTTP 200 but was actually an ArcGIS error body (`{"error":{"code":400,"message":"Invalid URL"}}`) — a reminder that a 200 status alone doesn't mean a URL is real for these services. Documented the correct discovery method in `boundaries.py`'s module docstring for future layers.
- Confirmed and used 4 real layers, each verified live by querying it and checking the response against the spec's stated codes:
  - **Parish BFC** (`Parishes and Non Civil Parished Areas (December 2023) Boundaries EW BFC`) — Cholsey E04012474 present, name matches.
  - **Parish BGC** (same vintage, generalised clipped, for display).
  - **LSOA BFC** (`Lower layer Super Output Areas (December 2021) Boundaries EW BFC (V10)`) — both E01035751 ("South Oxfordshire 015H") and E01028619 ("South Oxfordshire 015B") present, names match spec exactly.
  - **Ward BFC** (`Wards (December 2020) Boundaries UK BFC`) — E05011701 ("Cholsey") present, name matches. December 2020 is a **working assumption** for the vintage matching Forest Research's "2020 imagery" canopy dataset — not yet confirmed against that dataset's own metadata. Logged as **Q-008**.
- `pipeline/src/cholsey_pipeline/geography/boundaries.py`: a `LAYERS` registry of the 4 verified layers, `fetch_boundary()` (live query + manifest write to `data/manifest/boundaries/`), and `parse_boundary_response()` (pure parsing function, separated so tests don't need network — development-plan.md §5.1).
- **Bug caught by writing the tests, not shipped:** the first version fetched geometry without an explicit output spatial reference. ArcGIS's `f=geojson` defaults to WGS84 (lon/lat degrees) unless `outSR` is set, but the GeoDataFrame was being labelled `EPSG:27700` (British National Grid, metres) regardless — so `.geometry.area` silently computed a near-zero garbage value in the wrong units. A test asserting Cholsey's area was in a sane km² range caught this immediately (`0.00 km²` is not subtle). Fixed by requesting `outSR=27700` explicitly, with a comment explaining why, and regenerated the fixtures.
- **Real, useful finding from building the parish fixture:** querying by parish *name* for "South Stoke" returns **two different parishes** with different GSS codes (E04008163 and E04009876) — there's more than one South Stoke in England & Wales. This is exactly why development-plan.md's P1.3 says to select comparators by polygon adjacency, never by name — now backed by a real example rather than a hypothetical, and pinned in a test (`test_two_south_stokes_exist_by_name`) so it can't be silently lost if fixtures are regenerated.
- `pipeline/tests/fixtures/boundaries/`: three small, real, trimmed GeoJSON fixtures (parish ×5 features ~113KB, LSOA ×2 ~34KB, ward ×1 ~32KB) and `pipeline/tests/unit/test_boundaries.py` (10 tests: fixture parsing, the area sanity check, the two-South-Stokes finding, ArcGIS error/missing-field handling, registry sanity). 32/32 pipeline tests passing overall.
- **P1.2 verification result:** every GSS code in spec §2 (parish, ward, both LSOAs) checked out exactly against live ONS data — no code discrepancies. **One real, unexplained discrepancy did turn up**: the live ONS BFC parish polygon area for Cholsey is ~15.91 km², not the 16.52 km² spec §2 states (~3.7% off, not a rounding artefact). Logged as **Q-007** rather than silently changing `config/geography.yaml`'s `area_km2` (per CLAUDE.md: don't decide spec-level discrepancies unilaterally). Also noted, as a minor clarification rather than a real problem: the actual ONS dataset title says "EW" (England & Wales), not "UK" as spec §2's shorthand suggests — expected, since Scotland/NI have no equivalent civil parish geography.
- Updated `config/sources.yaml`'s boundary entries with the real, verified URLs (replacing the generic `https://geoportal.statistics.gov.uk/` placeholder from P0.4), split the parish entry into BFC/BGC (they're genuinely different datasets), and added the ward source. Each entry's notes cross-reference Q-007/Q-008 where relevant.

## Handoff notes
- If you're building P1.3: `fetch_boundary("parish_bfc", codes=[...])` and `fetch_boundary("parish_bfc")` (no codes = everything, this layer is small enough) are both available now. Remember the South Stoke trap — always disambiguate candidates by geometry/adjacency, never trust a name match alone.
- If a future ONS layer needs adding (e.g. for P2's MSOA/district/national boundaries, if those turn out to be needed as polygons too): don't guess the FeatureServer URL. Use the same `geoportal.statistics.gov.uk/api/search/v1/collections/dataset/items?q=<words>` search, find the right item, then read its `properties.url` — see the module docstring in `boundaries.py` for the exact method, and the `test_all_layers_point_at_the_ons_arcgis_org` test that guards against a hand-typed URL sneaking in.
- `_write_manifest()` in `boundaries.py` is untested by this run's test suite (it's a real filesystem side-effect of `fetch_boundary()`, which itself needs live network and wasn't exercised in CI) — worth a lightweight test with a temp directory if P1.3 or later work starts relying on manifest output being correct.
