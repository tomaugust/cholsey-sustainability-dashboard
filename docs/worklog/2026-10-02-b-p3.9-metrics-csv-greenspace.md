# 2026-10-02 — Greenspace added to metrics.csv

- **Phase / tasks:** P3.9
- **Branch / PR:** `phase-3-metric-table` / not opened
- **Agent / person:** agent (routine firing)

## Goal

Extend the real `data/processed/metrics.csv` to cover metric 2
(accessible greenspace), the last of the four buildable core metrics
still missing from it (canopy and electricity/gas were completed in
earlier firings this same day).

## Done

- `scripts/build_metrics_csv.py` gained `_build_greenspace_rows`,
  `_build_greenspace_district_row`, `_build_greenspace_national_row`,
  and `_fetch_census_2021_population` (a small live nomis helper for the
  district/national population denominators, re-fetched live rather than
  hardcoded from memory, same dataset P1.6/ADR-0005 already uses).
- Subject/comparator rows: fetch all 9 areas' real parish boundaries in
  one call, fetch OS Open Greenspace sites once for the combined bbox,
  clip each area's own geometry, call the already-existing
  `compute_subject_greenspace_row` -- no new ambiguity to resolve here
  (unlike canopy's Forest Research vintage matching), so no hand-
  maintained mapping was needed, just live fetch + clip.
- District row: South Oxfordshire's own boundary + its own greenspace
  fetch + `compute_subject_greenspace_row(..., area_role="district")`,
  with its real Census 2021 population (149,085, re-verified live via
  nomis, not hardcoded).
- National row: reused the exact simplify/within/clip performance
  pattern the original P3.3 national-row firing established (England's
  real BFC boundary is too complex, 20MB WKB, to clip ~150,000 raw site
  polygons against directly in a reasonable time). Ran the full script
  via a background shell (`run_in_background`-style) with a `Monitor`
  task watching for completion, rather than blocking the session on a
  ~13-minute live fetch -- real timings: 150,756 England sites fetched
  in ~497s, full simplify/within/clip pass in ~301s more (~798s total
  for this one step).
- Smoke-tested the non-national parts in isolation first (direct
  function calls, not through `main()`) before committing to the long
  full run, catching nothing wrong -- the district row's real value
  (45.2615450544583 m²/resident) matched the already-documented 45.26
  exactly on the first real run.
- **Real finding, investigated properly before accepting**: three
  comparators' values from this run differ from prose figures recorded
  in STATUS.md/worklogs from the *original* P3.3 firing (2026-09-30) --
  Wallingford 42.75→43.72, Crowmarsh 56.58→57.60, and more substantially
  Brightwell-cum-Sotwell 26.31→20.00 m²/resident (a ~24% difference).
  Investigated rather than assumed either figure was right:
  - Re-ran Brightwell-cum-Sotwell's clip completely independently (a
    direct single-parish `fetch_boundary`/`fetch_greenspace_sites`/
    `gpd.clip` call, bypassing this script's multi-parish bbox logic
    entirely) and got the **identical** 19,998.29 m² accessible /
    20.00 m²/resident result -- ruling out a bug in the new integration
    code's bbox/clip handling.
  - Confirmed the raw OS Open Greenspace zip file itself is
    byte-identical to the original 2026-09-30 fetch (`fetch_file`'s
    conditional request returned "unchanged," same sha256) -- ruling out
    the live OS dataset having genuinely changed in the meantime.
  - Conclusion: the original P3.3 firing's prose figures for these three
    comparators (Wallingford/Crowmarsh/Brightwell-cum-Sotwell) were never
    captured in a committed, tested fixture the way Cholsey/Moulsford/
    Aldworth's were -- only printed from a one-off exploratory script's
    terminal output at the time. This run's figures, produced by the
    real, unit-tested `compute_subject_greenspace_row` function against
    freshly (and independently re-verified) fetched data, are the
    authoritative ones going forward. Documented transparently here
    rather than silently overwriting a previously-stated number without
    comment.
  - England's national total also shifted marginally (1,941,454,012.58 m²
    vs the original 1,940,711,368.31 m², ~0.04% difference) despite
    identical raw site data -- attributed to the 50m-tolerance
    `simplify()` step's boundary-precision sensitivity (a handful of
    sites near the simplified coastline can flip between the fast
    `.within()` path and the exact-clip path depending on minor
    differences in how the England boundary's vertices were paginated/
    reassembled across two separate live fetches). This is noise within
    the already-documented, deliberate performance tradeoff
    (ADR-0009-adjacent reasoning), not a new correctness concern.
- Real result: **43 rows** now in `data/processed/metrics.csv` (was 32).
  All four buildable core metrics (canopy, greenspace, electricity, gas)
  now have complete subject+comparator+district+national coverage in the
  real, live-generated pipeline output.
