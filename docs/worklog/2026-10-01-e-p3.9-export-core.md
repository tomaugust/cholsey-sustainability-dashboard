# 2026-10-01 — P3.9's export.py core assembly (ADR-0010)

- **Phase / tasks:** P3.9
- **Branch / PR:** `phase-3-metric-table` / not opened
- **Agent / person:** agent (routine firing)

## Goal

Resolve the P3.9 design gap flagged repeatedly in prior worklogs (P3.2's
2026-10-01 handoff note, most recently): none of the four metric row
dataclasses carry the provenance columns `METRICS_CSV_SCHEMA` requires.
Unblock `export.py` by deciding how provenance reaches each row, then
build and test the core assembly logic.

## Done

- Reviewed `METRICS_CSV_SCHEMA` (`validate/metrics_schema.py`) and all
  four metric row dataclasses (`CanopyMetricRow`, `GreenspaceMetricRow`,
  `EnergyMetricRow`, `UptakeMetricRow`) in full before deciding anything
  -- confirmed they share exactly the same 11 base fields plus one
  module-specific extra each, and confirmed the schema is `strict=True`
  (no extra columns allowed), so whatever assembles the final row must
  select only the shared fields, not just merge everything.
- Investigated manifest shapes across fetchers before picking a
  provenance-lookup design: `fetch.http.fetch_file`'s manifests use a
  `sha256` key and no `query_signature` unless `record_row_count` adds
  one later; `geography.boundaries.fetch_boundary` and this session's new
  `fetch.forest_research_canopy.fetch_ward_canopy_for_country` (both
  multi-page, writing their own manifest directly) use `response_sha256`
  and always set `query_signature`/`where_clause`. Concluded that
  re-discovering "which manifest entry backs this row" after the fact
  would be fragile -- `forest_research_canopy` alone now has manifest
  entries from three different real queries this session (single wards,
  9 comparator wards, 6,135 England wards), so "latest for this
  source_id" would often be the wrong one.
- Wrote **ADR-0010**: `export.build_metrics_row` takes an already-computed
  row plus the specific live fetch's own `retrieved_at`/`raw_sha256`
  (known to whichever script orchestrates "fetch → compute → assemble,"
  right after that fetch returns) and the loaded `sources.yaml` registry
  -- not threaded through the pure `compute_*_row` functions (which have
  no I/O today and shouldn't gain config-loading just for this), and not
  re-derived from a manifest lookup afterwards.
- Built `pipeline/src/cholsey_pipeline/export.py`:
  - `build_metrics_row(row, *, source_id, retrieved_at, raw_sha256,
    sources) -> dict` -- pure function, raises `ExportError` on an
    unknown `source_id` or an empty `retrieved_at`/`raw_sha256` (never
    silently writes a null provenance value).
  - `rows_to_dataframe(rows) -> pd.DataFrame` -- validates against
    `METRICS_CSV_SCHEMA`, stable column order.
  - `write_metrics_csv` / `write_readme` -- the latter writes the
    human-readable "latest value per metric per area" summary P3.9 wants
    (one markdown table per `metric_id`, latest year only per area),
    headed with a "do not hand-edit, regenerated every run" notice
    (CLAUDE.md: never hand-edit generated data).
- Tests use real data already produced this phase rather than synthetic
  fixtures: P3.2's real national canopy row (14.41%, England,
  `flag=partial_coverage`) and the real `forest_research_canopy` manifest
  entry's actual `retrieved_at`/`response_sha256` from the England-wide
  fetch earlier this session.

## Handoff notes

- If you're building the P3.9 integration script: for each area/metric,
  capture provenance immediately after the fetch call returns, not
  afterwards -- `fetch.http.fetch_file` returns a `FetchResult` with
  `retrieved_at`/`sha256` directly; `geography.boundaries.fetch_boundary`
  and `fetch.forest_research_canopy.fetch_ward_canopy_for_country` don't
  return one, so read the manifest file they just wrote (their directory,
  `data/manifest/<source_id>/`, sorted, newest file) right after the call
  while it's unambiguous which one is "the" fetch that just happened.
- `export.build_metrics_row`'s `sources` parameter is the dict
  `registry.load_sources()` returns (keyed by `source_id`, each entry's
  `name`/`publisher`/`url` fields are used) -- pass the real loaded
  registry, not a hand-built dict, once this moves from tests to the real
  integration script.
- Module-specific extra fields (`accessible_area_m2`, `total_mwh`,
  `estimated_installations`, `pct_of_parish_area`) are deliberately
  dropped by `build_metrics_row` -- they don't belong in `metrics.csv`
  (schema is `strict=True`). Whatever eventually builds the site JSON
  (P3.9's other half, not done this firing) will likely want these, so
  keep them available from the original row objects rather than only
  from `build_metrics_row`'s output.
