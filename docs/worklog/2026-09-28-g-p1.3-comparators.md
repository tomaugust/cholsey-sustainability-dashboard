## Done
- Queried the live ONS parish layer for everything within a 5km-buffered bounding box of Cholsey (46 candidate parishes), fetched full geometries for those, and computed which ones actually intersect Cholsey's polygon (buffered 5m to tolerate BFC clipping precision gaps — verified the result is identical at buffer sizes 0m/1m/5m/20m, so this isn't a precision artefact).
- **Result: 8 real touching parishes**, not the spec's 5: Wallingford, Moulsford, South Stoke, Brightwell-cum-Sotwell, Aston Tirrold, **Aldworth, Crowmarsh, South Moreton** (the last three not in spec §2 at all).
- **Two real errors in the spec's candidate list, found by checking real data rather than trusting names:**
  1. "South Stoke" — already known from P1.1 that two different parishes share this name; confirmed here that the correct one (E04008163, the one that actually touches Cholsey) was selected, not the other (E04009876).
  2. **New finding:** spec §2 lists "Aston Tirrold & Aston Upthorpe" as one candidate. They're two separate civil parishes with separate GSS codes. Only Aston Tirrold's polygon touches Cholsey's — Aston Upthorpe borders Aston Tirrold, not Cholsey, and is correctly excluded.
- `pipeline/src/cholsey_pipeline/geography/comparators.py`: `find_touching_parishes()`, a pure function (no network) over a GeoDataFrame, so it's testable against a fixture.
- `pipeline/tests/fixtures/comparators/parishes_near_cholsey_sample.geojson`: 11 real parishes (Cholsey + the 8 touching + 2 non-touching controls — Aston Upthorpe, to prove the spec's pairing is wrong, and Didcot, a distant sanity check).
- `pipeline/tests/unit/test_comparators.py`: 6 tests, including one that pins the exact 8-parish result, one specifically proving Aston Upthorpe is excluded, and one checking the result is stable across buffer sizes. 39/39 pipeline tests passing overall.
- **`docs/decisions/0003-comparator-parish-selection.md`** (Proposed): documents the method, both findings, three options (all 8 / spec's original 4 / a curated subset), and recommends all 8 as the most defensible literal answer to "which parishes touch Cholsey" — while being explicit this is a recommendation, not a decision, since it changes the comparator count spec §6's UX sections seem to have assumed (a 5-candidate framing).
- **Q-009** logged in `STATUS.md`, using the new answer/action-tracking format from this morning's protocol change — `open`, empty answer cell, waiting on Tom.
- `config/geography.yaml`: replaced the 5 `PENDING-*` name-only placeholders with the 8 real GSS codes (all still `pending_confirmation: true` until Q-009 is answered), each annotated with whether it was in the spec's original list and why (or why not, for Aston Upthorpe).
- Updated `test_comparator_parishes_are_explicitly_flagged_pending` (P0.4-era test) to check for real GSS codes + the `pending_confirmation` flag instead of the now-retired `PENDING-*` key prefix, and added a new test pinning the exact 8-name comparator set.

## Decisions
- **ADR-0003 written as Proposed**, not self-accepted — per CLAUDE.md's explicit rule that comparator selection is a scope decision for the project lead, not an agent. The computation and its two findings are facts; which final set to use is Tom's call (Q-009).
- Judgement call, not needing its own ADR: used a 5m buffer for the touching test, chosen because BFC (full-resolution clipped) boundaries can have tiny gaps at shared edges from independent clipping/simplification of adjacent polygons. Verified this choice doesn't change the answer across 0–20m, so it's a robustness margin, not a decision that shapes the result.
