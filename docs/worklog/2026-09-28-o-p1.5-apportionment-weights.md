## Goal
Compute, for every (parish, LSOA) pair P1.4 identified, a real address-count apportionment weight plus an area-based cross-check, and the equivalent (parish, ward) area weight for the ward-level canopy dataset — development-plan.md §3 Phase 1, P1.5.

## Done
- Checked `STATUS.md`'s Open questions first (plan §4.7): Q-005, Q-007, Q-010 remain genuinely open with no answer from Tom — nothing to action ahead of the task queue this firing.
- **Found a real, queryable source for UPRN counts**: the ONS National Statistics UPRN Lookup (NSUL, January 2024) — not a FeatureServer like P1.1/P1.4's lookups, but a per-GB-region CSV-in-zip download (South East region ≈1.6GB uncompressed, vs. ONSUD's full ~40M-row national file). Downloaded via the ArcGIS Hub item's `/sharing/rest/content/items/<id>/data` endpoint (discovered via the same Geoportal search API pattern as P1.1), then filtered immediately to the 15 OAs P1.4 had already identified as relevant to Cholsey/Moulsford — counted, and the 485MB zip discarded (not committed; `data/raw/` is gitignored).
- Real counts obtained: `E01035752` (the LSOA split between Cholsey and Moulsford) has 487 UPRNs on the Cholsey side and 348 on the Moulsford side (835 total) — an address-count weight of **Cholsey ≈0.583**, compared to P1.4's coarser 3-of-5-OA proxy of 0.6.
- **Also fetched live parish/LSOA/ward polygons** (via the existing `geography.boundaries.fetch_boundary`) to compute a genuine area-based cross-check, as the plan requires. Real finding: the same split LSOA is only **≈0.457** Cholsey by area — a materially different number from the 0.583 address-count weight. The Cholsey-side addresses are measurably denser than the Moulsford-side ones. This is exactly why the plan asks for area as a cross-check, not a substitute — documented in ADR-0004 with a recommendation that Phase 2/3 apportion LSOA-level consumption data using the address-count weight, since consumption is a per-meter (per-address) quantity.
- **Also computed the (parish, ward) area weight for canopy**: Cholsey parish sits entirely (weight 1.0) inside the "Cholsey" ward (E05011701) — but that ward's own polygon is ~4x the area of the parish (a real, slightly surprising finding: the ward bundles in nearby area beyond just the parish). No apportionment complexity needed for Cholsey specifically (only one ward), but the function (`compute_parish_ward_weights`) handles the general multi-ward case for any future parish that does span more than one.
- New module `pipeline/src/cholsey_pipeline/geography/weights.py`: `compute_address_weights`, `compute_lsoa_area_weights`, `compute_parish_ward_weights` — pure functions, no network, tested against real fixtures (`pipeline/tests/fixtures/weights/`, `pipeline/tests/unit/test_weights.py`, 9 new tests, 53 total passing).
- New script `pipeline/scripts/build_weights_csv.py` — combines a committed reference-data extract (`geography/reference_data/oa_lookups_cholsey_area.json`: the real OA→parish/OA→LSOA rows plus the NSUL counts, with provenance) with a live boundary fetch, and writes `data/processed/geography/weights.csv` (10 rows: 4 address_count, 5 area_cross_check/area, with every provenance column populated — source, URL, vintage, retrieved_at, method, flag). Not wired into `make refresh` (still a Phase 2/3 stub) — this is a one-off Phase 1 geography build, run manually, matching how P1.1-P1.4's live-verified findings were committed.
- New `config/sources.yaml` entry: `ons_nsul_uprn_lookup`.
- `config/geography.yaml`'s `lsoas:` section comment updated to point at the real weights now available, with the concrete numbers, instead of just warning not to use `oa_count_share` as final.
- **ADR-0004** (Accepted, technical implementation choice — not a scope/spec/stack decision needing Tom's sign-off): records three methodology choices — (1) NSUL over the full ONSUD, since NSUL already uses the same OA best-fit assignment P1.4 relies on; (2) whole-address (not residential-only) counts, since NSUL has no property-type field and a real residential split needs paid AddressBase Premium data; (3) scope limited to Cholsey/Moulsford, matching P1.3/P1.4's precedent, with comparator-level apportionment logged as a new backlog item in `STATUS.md` rather than done speculatively.
- `.gitignore`: added `data/manifest/` (timestamped per-run fetch records from `fetch_boundary`'s manifest-writing) — these were never previously committed and would just accumulate diff noise on every re-run; the provenance that matters long-term is already in `weights.csv`'s own columns and `sources.yaml`.

## Decisions
