## Goal

A Phase 3 exit-criteria review in a prior firing (this session) found two real gaps: (1) `metrics.csv`'s energy rows only ever carried the latest year, not "all available years" as development-plan.md's Phase 3 key outcomes require; (2) no ADR existed for the `suppression_fallback` method, despite it being a defined flag and an exit-criteria expectation. This firing closed both, and investigated a crash hit while verifying the fix end-to-end.

## Done

- **P3.9: multi-year energy.** `pipeline/scripts/build_metrics_csv.py`'s `_build_energy_rows_for_fuel` now loops over `ENERGY_YEARS = range(2010, 2025)` for subject/comparator rows (LSOA-level DESNZ data, verified live to cover this full range for both fuels) instead of a single hardcoded year.
- **Root-caused why district/national rows can't use the same range, for BOTH fuels — not just electricity as an earlier pass in this same firing first assumed.** Two independent upstream issues, both verified by reading the real downloaded DESNZ workbooks directly (`openpyxl`, not guessed):
  1. Electricity's regional/LA sheet changed column layout between 2011 and 2012 (`parse_regional_la_sheet`'s header check is written for the 2012+ layout only).
  2. **New this firing**: both fuels' regional/LA sheets identify country/LA rows by an old pre-GSS code scheme in 2010-2011 (confirmed directly: South Oxfordshire's `Code` cell is `38UD` in the 2010/2011 gas sheet, `E07000179` from 2012 on; England's row has a blank `Code` pre-2012). `parse_regional_la_sheet` filters by GSS `area_codes`, so pre-2012 country/LA rows silently match zero records — no exception, just fewer years than requested. This is what an earlier pass in this firing saw as "gas returns 13 of 15 years with no error" and left unexplained; tracing it down to the actual workbook cells resolved it.
  - Fixed by renaming the single-fuel `ELECTRICITY_REGIONAL_LA_YEARS` to a shared `REGIONAL_LA_YEARS = range(2012, 2025)`, applied to both fuels' district/national fetch. LSOA-level rows are unaffected (DESNZ's LSOA sheets have always used GSS-equivalent LSOA codes).
- **ADR-0011 written** (`docs/decisions/0011-suppression-fallback-deferred.md`): formally defers the `suppression_fallback` flag/method. `fetch/desnz_postcode_energy.py` (P2.6) exists and documents DESNZ's real suppression rule, but no LSOA this project actually uses has ever come back suppressed in a live fetch — nothing to build a fallback from yet. Documents the trigger condition for revisiting (a future `fetch_lsoa_energy` call returning fewer records than a known LSOA count).
- **Q-012 raised** in STATUS.md: development-plan.md §3's literal P3.8 reconciliation test ("summed apportioned meter counts across all parishes in the district match within 1%") can't be satisfied as written, since this project only builds apportioned rows for 9 of South Oxfordshire's 60+ constituent parishes (ADR-0003/Q-009's explicit scope decision). Needs Tom's steer on how to reword the test before P3.8's fourth check can be built.
- **Diagnosed and root-caused a mid-run crash as a genuine external outage, not a code defect.** See "Verification" below for the full trail.

## Verification

- `ruff check --fix` / `ruff format`: clean.
- `pytest -q`: 300 passed (unchanged count — this script has never had dedicated unit tests, consistent with its existing live-run-verification pattern).
- Live run (`build_metrics_csv_run3.log`): canopy subject+comparator+national all succeeded (Cholsey 10.40%, England 14.41%, matching previously-verified figures exactly). Electricity and gas subject/comparator rows: 8 of 9 areas got the full 15 years (2010-2024), Moulsford got 10 (2015-2024, its own LSOA's real coverage — not an error). The run then crashed inside canopy's district row (`_fetch_current_wards_for_lad`, `KeyError: 'features'`) before reaching greenspace this time (an earlier run in this firing crashed one step later, inside `_build_greenspace_rows`'s `fetch_boundary("parish_bfc", ...)`, with a `400 Bad Request`).
- **Outage root-cause trail**: both crash points call ArcGIS FeatureServer endpoints on the same ONS Geoportal org, `services1.arcgis.com/ESMARspQHYMw9BZ9`. Direct `requests`/`curl` calls against the exact URLs (`parish_bfc`'s FeatureServer/0/query, the ward-to-LAD lookup FeatureServer, and even each service's own root `?f=json`) all returned `{"error":{"code":400,"message":"Invalid URL"}}` — including for a *different* FeatureServer in the same org (`Non_Civil_Parished_Areas_Dec_2019...`), ruling out a URL/casing/rename issue specific to one dataset. The ward-to-LAD lookup's root returned a different, .NET-style error (`"Layer 'WD20_LAD20_UK_LU v2' does not exist or is inaccessible."` / `"Object reference not set to an instance of an object."`). Cross-checked the org's own service directory listing (`.../arcgis/rest/services?f=json`) — both services are still listed there, at exactly the URLs this codebase already uses. Conclusion: a genuine, org-wide ONS ArcGIS hosting disruption affecting multiple unrelated services at once, not a wrong URL, not a renamed/retired dataset, and not a bug in `fetch_boundary`/`_fetch_current_wards_for_lad` (both have this exact call pattern succeeded many times earlier in this same session). This is consistent with the `ReadTimeout`s hit against the ONS Postcode Directory service (same org) earlier in this firing while investigating the suppression-fallback ADR.
